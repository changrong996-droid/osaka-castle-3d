## 先回答委托人的问题

「一张图，四种形态，共用一个编号」今天是**手工巧活**，但它的骨架已经具备成为**新图纸形态第一例**的条件。判据只有一条：**换一座站，内核不动，这套编号和四个槽位还能立起来**。今天只有「生长」一个形态是真的（规则推导 + 排程 + 同源出图），「图纸」是三张现成函数，「成品」是同一模型的终态，「实物」是空的；它们之间靠一张还没写出来的登记表相连。所以现阶段证据支持「样板」，不支持「形态」。分水岭是第二站，不是第一站做得更漂亮。

有一个认识要先立住，后面每一条都从它推出来：**图号锁的是「取景框」，不是「主体」，也不是「时刻」**。S-301-3 是「x = 39 m 的横剖面」这个框，框里的主体是活动键（`wlift`）和构件（`J23`），框里的时刻是时间轴坐标。四种形态能共用一个编号，正是因为编号不含时间、不含状态——同一个框在不同时刻、不同形态下出现四次。一旦编号开始携带时间或状态（「提升完成图」「2021-06-28 版」），四形态就塌回四套图纸。

## 第一部分 三层想象

### 第一层 把这一册本身做到极致

**是什么样。** 六个页号全部有图，不再是「待出图」标签；每个活动都能在登记表里找到至少一个取景框；「成品」槽位有验收字段，模型里程碑（`K.wlift.end`、`K.clad.end`、`P.OPEN`）与公开节点（2021-06-28、2021-08-31、2022-09-22）在同一张表上并排，偏差以天计；「实物」槽位对每个公开节点至少有一条按机位对齐的照片，在同一机位 `cam` 与同一时刻 `t` 下，三维能半透明叠在照片上，观众一眼看出哪里对、哪里不对。大电视上它是一条能自动播放、字号够大、不需要鼠标的讲解：时间轴走，三维长，右栏图纸换，图号一直挂在标题栏，照片在对应时刻淡入。家人与访客看的是「它是怎么长起来的」，业主看的是「推演和实录差了几天、差在哪一段」。

**要成立，需要什么为真。**
1. `window.__pv` 旁路接口在上游回路下活过第一阶段，或握手达成（方向备忘录 §2.1）。这是物理前提。
2. 公开照片的机位能配准到模型。模型几何是「推算」（`ASSUME`：柱网、分区边界、工期都是规则推出来的），不是测绘；配准只能到「说得过去」，不能到「毫米」。
3. 模型时刻与日历日期是两把尺。`HZ.dayDate(t)` 把模型天数按 `T0` 换成日期，这是**计划尺**；照片上的日期是**实际尺**。「推演完成 2021-06-xx vs 实录 2021-06-28」这一行文字（`hzview.js` 的 `i-assume`）已经在用两把尺，只是还没变成数据。
4. 大电视场景要求「零交互可看」：现有页面处处是鼠标交互（滚轮缩放千斤顶图、点吊点飞镜头）。极致版需要一个「放映模式」，但它必须是登记表驱动的（按图号顺序走），而不是另写一套脚本。

**最大的未知数。** 推算几何叠在真实照片上，视觉偏差会有多大，以及这种偏差是削弱说服力还是恰好构成「诚实的推演」这个卖点。这只能拿一张真照片试，不能推理出来。

### 第二层 推广到其他工程

**可复用的内核（换站不改）。**
- `core/seq.js`：活动对象、规则引擎 `derive`、排程 `schedule`、`auditNet`。它已经是通用的（大阪城与西站共用）。
- 构件记录的隐式 schema（盘点报告 2.2：`geo / act / st / du / rm / grp / sup / c / top`）与状态语义 `stOf` 的四态。
- 登记表格式 `HZA`（页 / 子图 / 四槽位 / 别名 / `resolve` / `wrapFn`）与实物记录格式 `HZR`。
- 无头基座与检查链（`harness / check_*`）。
- 图纸的图框与标题栏（`frame`、`ctx.tb`）、时间轴与放映的骨架。

**每站必须定制。**
- `build()`：400 行手工几何，全部是西站的柱网、网架、提升塔。
- 项目规则：`roofRule / sweepRule` 是「拼装→提升→合龙→整体提升→卸载」这一类屋盖的规则，另一类结构（比如盾构区间、桥梁转体、装配式住宅）规则完全不同。
- 四张绘制函数：`section / plan / lift / jack` 全部是提升阶段的图；另一座站的「关键图」可能是顶推曲线或吊装平面。
- 页号分类：`S-101 地下 / S-201 承轨层 / S-301 整体提升 / S-401 屋面 / S-501 开通` 把空间（楼层）与时间（提升、开通）混在一套编号里。这是西站的叙事顺序，不是通用分类法；第二站会有自己的一套。
- `P` 参数、`FACTS / SOURCES / ASSUME`、`CAM` 机位预设。

**数据产线的门槛在哪里。** 方向备忘录 §1.1 第 9 项已经定了顺序：先导出 `HZ.make()` 为 `parts.json` 金样，后做反向。门槛有三道，一道比一道难：
1. **schema 门槛**（便宜）：导出即得到显式 schema，这一步没有未知数。
2. **几何描述门槛**（中等）：`build()` 里大部分是参数化生成（柱网循环、网架格、每隔一格立胎架），不是逐个构件手写。所以产线的形态不是「一个巨型 JSON 列出 1 906 个构件」，而是「参数 + 生成器」——生成器要么是一组可复用的几何原语（`GB` 盒、格、杆），要么每站仍是一段代码。判断：**每站保留一段生成代码是可以接受的，前提是它只产出符合 schema 的记录，不碰内核**。
3. **规则门槛**（最难）：规则引擎通用，但规则本身依赖项目活动键（`K.lift1`、`wlift`、`head`）。推广要求规则用「活动的阶段 / 种类」而不是「活动的名字」来写。这一步决定第二站是「复制粘贴改一改」还是「真正的第二例」。

**要成立，需要什么为真。**
1. 第二站有足够的公开资料写出 `FACTS` 和一段 `build()`——这是内容门槛，不是技术门槛。
2. 内核对项目码、页号语义、活动键名零假设（见把关清单第 3、10 条）。
3. 第一站的登记表与记录格式不需要为第二站改字段名——只允许加可选字段。

**最大的未知数。** 规则能否脱离活动键名而写。今天 `roofRule` 的依赖链是硬编码的键名序列；如果第二站的关键工艺无法用「阶段表」表达，内核就得为每站开一个分支，那就不是形态而是作坊。

### 第三层 成为一种通用媒介或工具形态

**谁在用，什么场合。**
- 建设单位 / 业主：向非工程师汇报（董事会、政府、公众），需要「看得懂的过程」而不是甘特图。这正是大电视场景的放大版。
- 监理与施工方：周例会上把当周照片放进对应图号与时刻，看计划与实际差在哪一段。这是「进度核验」场景。
- 展厅 / 车站大厅 / 教育：建成后的「它是怎么来的」循环播放。
- 工程记录（竣工档案的叙事层）：不是替代竣工图，而是竣工图的「阅读入口」。

**与现有 BIM 与进度管理工具的关系。** Revit / Navisworks / Synchro / 广联达 BIM5D 做的是「权威模型 + 手工排程 + 挂接」，面向工程师，输入重、许可贵、输出是审查而不是阅读；P6 / Project 做的是排程，没有图；OpenSpace / Reconstruct 一类做的是「实拍 vs BIM」比对，需要 360° 采集与精细模型。这一册**不与它们竞争精度与合规**。它的位置是：**在它们之上的阅读层**——用规则推导（而非手工排程）得到过程，用同一数据源出图纸与三维，用图号作为工程师与非工程师的公共语言，用零依赖的浏览器文件作为载体。它从 BIM 工具取「事实」（真实构件、真实日期），自己负责「讲清楚」。

**差异化到底在哪里。** 三点，缺一不可：
1. **规则推导的过程**：排程是推出来的，所以改一条规则，整个过程重排；BIM 4D 是挂出来的，改一处要手工重挂。
2. **图号作为引用语言**：「看 S-301-3 第 850 天」是一句工程师和家人都能说的话；BIM 里没有这种可说的坐标。
3. **两把尺并排**：推算与实录在同一框里、同一编号下并置，而且永远标明哪条是推算——这是展示品变成核验工具的那一步，也是它比「做得精美的动画」诚实的地方。

**要成立，需要什么为真。**
1. 第二层成立（至少两个工程跑通，内核不动）。
2. 有一个外部读者（不是作者、不是协作者）用图号和时刻来讨论工程，而不是用截图。
3. 实物记录能从 BIM / 现场系统批量导入，而不是逐条手写——否则核验场景撑不过一周。

**最大的未知数。** 需求是否存在于作者之外。行业已经有「做得很重」的工具，缺的是不是「做得很轻、能读」的媒介，没有证据，只有直觉。这一层的所有投入都应该等第二层给出信号后再谈。

## 第二部分 把关清单

每条都是当下可执行的约束，针对第一阶段正在定型的三样东西：HZ-03 的登记表数据结构、HZ-05 的实物记录格式、方向备忘录 §1.4 的编号规则。

| # | 约束 | 保护哪个未来 | 违反的代价 |
|---|---|---|---|
| 1 | **图号只锁取景框。** 图号（页号、子图号、全号）不得含时间、版本、施工状态、形态；时间是坐标 `t`，主体是活动键 / 构件键 / `focus` 值，形态是槽位。 | 三层全部：四形态共用一个编号的根基 | 每个时刻、每种形态各一个图号，登记表爆炸，「共用一个编号」失效 |
| 2 | **两把时间尺分开记，不许互相换算填充。** 日历日期（实际尺）与模型时刻 `t`（计划 / 状态尺）各自独立字段；`t` 的定义是「记录内容的施工状态在模型里对应的时刻」，不是 `date` 减 `T0`；`null` 表示「尚未对齐」而不是「等于日期」。校验器不得断言两者相等。 | 第一层的核验价值（计划 vs 实际） | 差值永远是零，核验工具退化为展示品 |
| 3 | **项目码只出现一次。** `HZW` 作为一个常量（如 `HZA.PROJECT`），全号由常量拼接；代码、校验、`resolve` 不得写死 `'HZW-'` 字面量。 | 第二层（第二站） | 第二站全文替换，别名表与校验脚本跟着改 |
| 4 | **登记表是图号的唯一来源，代码不再产生编号。** 任何出现在标题栏、深链、DOM id 的图号必须能被 `HZA.resolve` 解析；别名只读；新代码不得写图号字面量（第一阶段函数内的 A 字面量按 §1.1 第 7 项清退）。 | 三层全部 | 两处来源打架（已发生过一次：A 系列） |
| 5 | **格式向前兼容。** `VERSION` 必填；新增字段必须可选且带默认；校验器对未知字段只警告不报错；字段顺序无语义。 | 第二层（加 `anchor`、`fit`、`val` 不返工） | 每加一个字段都是一次全量迁移，登记表与记录互相锁死 |
| 6 | **实物记录必须能指向主体。** 除了页号 / 图号（取景框），记录要能引用活动键或 `focus` 值（`J23`、`ZN`、`CUT`）；结构化信息不得藏进 `note` 自由文本。 | 第一层核验、第三层批量导入 | 照片只能「挂在页上」，不能「挂在构件上」，核验只能靠人眼 |
| 7 | **机位是模型空间坐标，与真实相机分开。** `cam` 的 `az el d tx ty tz` 只回答「在模型里从哪看」；真实相机参数（若有）另记；配准质量（手配 / 估算 / 实测）必须有字段，否则默认「手配」。 | 第一层叠图可信度 | 假精度：观众把手配的镜头当成实测 |
| 8 | **来源与许可是硬字段，但不得排斥自有素材。** `license` 必填；`url` 不得强制 `http` 开头——家庭照片、自拍实测、本地文件是大电视场景的主要素材。 | 第一层大电视场景、第三层私有数据 | 实物层只收得进新闻稿，收不进自己的照片 |
| 9 | **推算与事实永远分色。** 模型里的每个数（工期、尺寸、吨位）展示时带「推算 / 实录」标签；实物记录的核验结果只写进实物层，**不回写**模型参数与规则。 | 第三层差异化（诚实） | 观众把推演当真；或者模型为了「对上」照片被手工微调，同源失效 |
| 10 | **内核不读页号语义。** 检查脚本与通用代码不得假定 `S-101` 是地下、`S-301` 是提升；页号的含义只在项目登记表里；西站专用的检查（如「A 号别名不得解析到同数字 S 页」）必须标为项目级检查。 | 第二层 | 第二站的页号分类不同即崩，或者被迫沿用西站的分类法 |

### 3.2 HZ-05 实物记录格式

| # | 结论 | 意见 |
|---|---|---|
| 1 | 通过 | `id`（`R-0001`）是记录号不是图号；`sheet` 引用页号或短号，即引用取景框。 |
| 2 | **需改一处** | `t` 的约束栏写「施工日（天）」，与 `date` 并列时语义不清：读者会以为 `t = (date − T0) / 86400`，示例记录 `date: '2021-06-30', t: null` 又暗示两者独立。建议只改约束栏文字（字段名、类型、顺序不变）：`t` = 「记录内容的施工状态在模型中对应的时刻（天，可含小数表示小时；`0 ≤ t ≤ HZ.P.OPEN + 30`）；**不是**由 `date` 换算得来；`null` 表示尚未对齐」。`check_real` 保持不断言 `t` 与 `date` 的关系；可选：两者都非空时在 `OK` 行附带打印 `t − days(date)` 的偏差，作为第一个「计划 vs 实际」读数。S-301 时间轴按小时加权，允许小数是必要的。 |

## 第四部分 远景层面的不要追清单

1. **做成通用 BIM 平台或与 Revit / IFC 互通。** 这一册的价值是「从事实出发讲清楚」，不是成为事实的权威来源。一旦接 IFC，就要处理构件分类、几何精度、版本——那是别人已经做了二十年的事，而且会把「推算」偷换成「测绘」，违反把关清单第 9 条。
2. **照片测量 / 点云重建 / 三维重建。** 配准到「说得过去」就够了。做精细配准等于承认模型应该是测绘级，而模型的全部几何都是推算。
3. **AI 自动识别照片进度。** 诱人但不是这一册的瓶颈。瓶颈是「有没有一条对齐的记录」，不是「对齐得快不快」。先有一百条手工对齐的记录，再谈自动化。
4. **施工管理 SaaS（填报、审批、多人协作、权限、云端）。** 这是工具形态的另一端，意味着服务器、账号、合规。这一册的载体是一个浏览器文件，其轻量正是差异化所在。
5. **通用排程引擎与 P6 比较。** `core/seq.js` 的价值是「规则推导出过程」，不是资源平衡与工期优化。追求排程精度会把规则引擎做成第二个 P6，而且永远比不过。
6. **成品的质量验收系统。** 「成品」槽位的验收字段只做「模型里程碑 vs 公开节点」这一组。质量验收是法规与责任领域，不是媒介能承担的。
7. **第二套模型（无论是「精细成品模型」还是「实测模型」）。** 方向备忘录 §2.3 第 4 条已禁，远景层面同样成立：两套模型就有两套真相，同源卖点消失。
8. **在第二站出现前做反向数据产线（JSON → `build()`）。** 方向备忘录已定；远景补一句理由：产线的形态（参数 + 生成器 vs 纯数据）只有在看到第二站的几何之后才能定，提前做必然按西站的形状做。
9. **移动端 App、无人机巡检集成、VR / AR。** 展示终端是大电视与浏览器；核验的输入是一张照片加一个机位。任何新终端都是在未验证需求前增加表面积。
10. **把图号升级为全局唯一标识体系（URI、注册中心之类）。** 图号的力量在于「可以念出来」。`HZW-S-301-3` 够用；需要跨项目唯一时靠项目码（把关清单第 3 条），不靠体系。
