# PLAYBOOK：“规则生成施工 / 装配顺序”演示的通用做法

适用于：筑城（`web/build.html`）、码头小样（`web/port.html`）、杭州西站（`web/hzwest.html`，一屏 3D 英雄视图），以及以后的工厂、桥梁、F-35 机构图之类。
核心代码：`web/core/seq.js`（构件图 + 规则 + 排程 + 蒙特卡洛 + 审计 + 时间游标着色器）、`web/core/ui.js`（版式 / 叠层 / 图表）、`web/core/uiaudit.js`（界面审计）。
领域插件只写“有哪些构件、规则取什么参数、单价效率是多少”：`web/seqosaka.js`、`web/seqport.js`。

---

## 1. 怎么挑领域

值得做的领域同时满足：

1. **顺序由物理决定**：上面的东西压在下面的东西上（支承）、先挖后建、养护 / 固化 / 预压有硬性等待、临时设施要先搭后拆、长周期设备要提前订。规则越“物理”，生成的顺序越可信，观众越不会问“为什么先做这个”。
2. **构件能几何化**：每一类构件能用几个盒子 / 柱体 / 拉伸体表达，工程量（体积、面积、根数）可以从几何量出来。量不出来的东西（审批、谈判）只当成没有几何的“等待”活动。
3. **有能改变答案的参数**：观众手里的旋钮（规模、设备数量、工法、分期、开工日）要能让工期 / 投资 / 关键路径真的变。只能放动画、改不了答案的，做成视频就够了。
4. **观众有一个具体问题**：投资人问“多久、多少钱、什么时候开始挣钱、最大风险在哪”；工程师问“先做什么、谁在等谁”。页面第一屏只回答这个问题。
5. **规模合适**：50–500 个活动（步骤）。太少看不出规则，太多一帧画不完、浏览器里蒙特卡洛跑不动（码头：198 个活动，500 次蒙特卡洛 0.4–0.6 s / 方案）。
6. **数据可以用区间推算**：没有真实数据也行，但每个单价 / 效率要给一个“常见区间”，界面上标「推算」。

不合适：纯软件流程（没有几何）、顺序主要由人决定的事（会议、审批链）、需要精确结构计算才能定顺序的事。

## 2. 怎么把领域写成“构件族 + 规则”

### 2.1 构件族 → 活动
一个活动 = 一组同时施工的构件（`SEQ.act({...})`）：

| 字段 | 含义 | 从哪来 |
|---|---|---|
| `parts[].geo` | 几何（`SEQ.Geo`：box / hexa / prism / extrude），自动外向定向 | 领域插件按尺寸规则生成 |
| `kind` | build / remove（挖）/ fill（填）/ temp（临时，自动配拆除）/ procure / wait / milestone | 构件族决定 |
| `stage` | 工序名（规则按它挑对象） | 构件族 |
| `qty` / `tally` | 工程量 / 计数 | **从几何量出**（`geo.vol`、面积、根数） |
| `dur` | 工期（整数日） | 工程量 ÷ 效率（效率是参数） |
| `res` | 占用的资源（船机、班组、产线） | 构件族 |
| `cost` | 直接费 | 工程量 × 单价（单价是参数） |
| `env` / `excl` | 作业包络 / 净空互斥类 | 包围盒外扩（外扩距离是参数） |
| `unit` / `scope` / `phase` | 属于哪个泊位 / 区块 / 期 | 构件族 |

### 2.2 规则类型（`SEQ.RULE`，全部参数化，领域只给参数）

| 规则 | 类型 | 参数 | 码头里的例子 |
|---|---|---|---|
| R1 支承 | `support` | `on[阶段] = 可作支承的阶段`、`tol`、`minOverlap` | 横梁落在钢管桩顶、面板落在横梁上、岸桥落在轨道上 |
| R2 先挖后建 | `dig` | `to`、外扩 `e` | 港池疏浚先于该泊位沉桩 |
| R2 养护 / 满期（硬约束） | `cure` | `from`、`to`、`lag(a)` | 堆载预压 → 卸载，间隔 ≥ 满期 150 日（蒙特卡洛 120/150/210） |
| R3 阶段先后 | `after` | `to`、`from`、`scope`（同单元 / 同区块 / 任意）、`near`、`lag` | 吹填在护岸之后、联调在设备 / 电力之后 |
| R4 临时设施 | `temp` | 活动上的 `temp:{serves, removeStage, …}` | 施工栈桥服务 桩 / 梁 / 板 后拆除；堆载搭了必须卸 |
| R5 资源上限 | 排程参数 `caps` | 每类资源台数 | 挖泥船 / 打桩船 / 起重船 各 n 艘，陆上班组 4，安装队 2，岸桥产线 12 |
| R6 外部采购提前期 | `procure` | `lead(a) → {days, res, mfg, ship}`、`order(a)` | 岸桥 订货 → 制造 → 海运，安装 ≥ 到货 |
| R7 分期不干扰 | `phase` | `units`、`zone(u)`、`live(u)`、`margin` | 下期作业包络进入已投产泊位作业区 → 接口工程前置到该泊位投产前 |
| 净空互斥 | 排程参数 `excl` | `[类A, 类B, 净距]` | 岸桥吊装 × 打桩船 / 起重船、挖泥船 × 打桩船 |
| 闸门 | `gate` / `custom` | 前驱、lag | 施工许可；下期开工 = 上期首泊位投产 |

规则的顺序有讲究：先 `temp`（生成拆除活动），再 `support/dig/after`，再 `cure`（加大已有依赖的间隔），再 `procure`（生成采购活动），最后 `phase` 和闸门（需要前面的依赖才能求接口工程的前驱闭包，避免成环）。

### 2.3 排程（`SEQ.schedule`）
1. 拓扑排序（成环直接报出来）。
2. 无资源 CPM 求最迟开工 LS 作优先级（可加领域偏置：码头里前面的泊位略优先）。
3. 串行进度生成法（SSGS）：按优先级逐个放入，开工日 = 满足全部前驱 + 间隔、资源逐日剖面不超上限、作业包络不与互斥类同时在场的最早那天。
4. **关键路径 = 关键链**：从最后完成的活动回溯“决定它开工的那个约束”（前驱，或者它在等的资源 / 净空占用者）。所以关键路径会穿过资源排队（码头一次建成方案里穿过陆上班组和岸桥产线），比纯 CPM 真实。
5. 全部整数日 → 结果跨机器、跨架构逐位一致（x86 沙盒 / arm Mac / x86 VM 360 个配置 × 500 次 0 差异）。

### 2.4 不确定性与情景
- `SEQ.mc(N, seed, run, from, to)`：可分片、可复现（第 k 次的种子只由 seed 和 k 决定）。按工序类相关的三角分布 × 活动级小扰动；采购按制造 + 运输分别抽样。
- 分位数用**最近秩**（`SEQ.q`）：P50 / P90 一定是某一次真实排程的结果，不是插值出来的“不存在的方案”。
- 风险“此项延误 3 个月”：把该项工期（或满期间隔）+90 日后重排，**冻结基准**（`rel: a => a.start`，只许后移、先后照旧）。否则串行进度生成法会出现“延误反而提前”的异常。
- 方案对比 `SEQ.diff`：同一组指标 B − A。

## 3. 什么必须推出来，什么可以是参数

**必须推出（不许手填）**：依赖、顺序、开工 / 完工日、关键路径、工程量、船机·日 / 车次 / 工人·日、投资 S 曲线、投产日、P50 / P90、风险影响、审计数字。只要有一个是手填的，参数一改就穿帮。

**可以是参数（但要列进「假设」表、标「推算」、给区间）**：单价、效率、资源台数、提前期、养护期、分布区间、价格上涨率、利率、负荷爬坡、分期政策（下期何时开工、是否提前订货）。

**界面上的数字**：每一个都来自 `plan.at(t)` / 指标 / 蒙特卡洛结果；审计脚本逐个重算后与文字对比（码头：卡片、页眉、差值表、风险表、甘特条数与游标、S 曲线读数、提示框）。

## 4. 怎么验证（全部保持 0）

| 层 | 检查 | 工具 |
|---|---|---|
| 规则 | 无支承、成环、依赖违例（开工早于前驱完成 + 间隔）、R4 违例 / 竣工残留、R5 峰值 > 上限、R6 早于到货、满期不足、R7 冲突（独立重算包络相交，不读规则生成的依赖）、净空互斥冲突、临时杆件净空碰撞（`SEQ.clearance`） | `SEQ.auditNet`（页面实时 + node） |
| 全参数空间 | 所有参数组合都跑一遍上面的审计 + 风险非负 + 蒙特卡洛 | `work/port/sweep/sweep.js`（可多机分片） |
| 数字 | 界面每个数字 == 重算值 | `work/port/mac/audit_port.js` |
| 版式 | 截断、被祖先裁掉、出屏、叠层互压 / 出界、面板互压、SVG 文字互压 / 出框、3D 区保底、整页不滚动、图标字形 | `web/core/uiaudit.js`（只数真的看得见的元素） |
| 交互 | 每个按钮 / 滑块 / 快捷键 / 拖动都要改变状态 + 画面（或 DOM） | `work/port/mac/audit.js` |
| 真 GPU | Mac M4 Metal：9 视口审计 + DPR 2 帧率 | Mac 上的 Playwright + 系统 Chrome |

视口至少包括：1440×900、1920×1080、1280×720、1024×768、2000×860、1728×1000、1512×860、1440×760、**1258×540（用户真实的矮窗口）**。

## 5. 版式法则（给人看，不是给机器看）

**先问：观众第一眼要看到什么变化？** 杭州西站 r2 起，演示类页面的默认：左 3D 墨线图 + 右栏 2–3 张由同一模型实时出的图纸 + 3D 角上 3–5 行真实检查计数，写实只做结尾；更早（preview1）的默认是：一个大 3D 主视图就是答案，外加 1 条时间轴 + 1 行字幕 + ≤ 3 个实时数；其余（假设、来源、自检）放在一个小按钮后面。投资对比、甘特、S 曲线只在观众真的要“比方案”时才上，而且不和 3D 抢同一屏。


- 第一屏就是答案：页眉 4 个数（码头：总工期 P50/P90、总投资、设计吞吐、首泊位投产），B 的值和 Δ 紧跟在旁边。
- 核心信息一屏看全，不滚动；次要信息（假设、工程量全表、自检明细、方法）点开第二层。
- 3D 区保底 300 px（含控制条）；按窗口实测分配高度（`UI.fitRows`），矮窗口先收小字、合并甘特行、收起次要块。
- 叠层（方案卡片、工具条、图例、图钉、提示框）互不重叠：`UI.Overlays` 逐级收起，`UI.placePins` / `UI.placeBox` 找空位，找不到就隐藏。
- 相机取景到“叠层之间的空带”（`setViewOffset` 把投影中心下移），模型不躲在卡片后面。
- 只在变化时渲染（dirty 标志）；图表 / 图纸按键缓存（`UI.memo`），不每帧重建。

## 6. 踩过的坑与修法

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | OrbitControls 吞点击 | 叠层按钮鼠标点击全部无效（19 个）：pointerdown 时 `setPointerCapture` 把 click 改投给画布 | 叠层 / 面板 `pointerdown` stopPropagation（`UI.stopOrbit`）；控制器只挂在 3D 区 |
| 2 | 矮宽窗口压扁 3D | 1258×540 下 3D 只剩 198 px，控制条压在模型上 | 版式按窗口实测；控制条移出 3D 区；3D 保底；放不下才整页滚动（并审计报出） |
| 3 | 标注互压 | 时间轴标签、图纸标高、甘特行名、图钉互相压 | 按像素实测宽度排布（`UI.pickLabels`），放不下就不画；行高 ≥ 1.45 × 字号（中文 SVG 文本包围盒比字号高），矮窗口合并甘特行（11 → 8 → 6） |
| 4 | 图标字体豆腐块 | ⏮⏭▶❚❚ 走字体回退显示 ▯ | 只用内联 SVG 图标（`UI.icon`）；审计用字符范围查 |
| 5 | 跨架构浮点差 | 早期烘焙包在 x86 / arm 上逐字节不同 | 时间全用整数日；随机数用 `Math.imul` 的 mulberry32；只在一个地方烘焙或量化；码头扫描 x86 / arm 0 差异 |
| 6 | 每帧重画图纸 / 图表 | 竣工静止时 48 fps | 图纸渲染到缓存纹理、图表 `UI.memo`，时间变化才重画；只在 dirty 时渲染 |
| 7 | 审计数到隐藏元素 | 139 条“标注出框”，其实是 display:none 的破风标注 | 可见 = 自身和所有祖先都可见且有面积（`__vis`）；隐藏要连子元素一起隐藏 |
| 8 | 单一数字不可信 | 投资人问“这个工期有多大把握” | 蒙特卡洛 P50 / P90（最近秩）；假设表 + 区间 + 「推算」 |
| 9 | 延误反而提前 | 软基满期 +90 日，首泊位 −13 日（串行进度生成法的 Graham 异常） | 延误分析冻结基准（不早于基准开工、先后照旧）→ 2 592 个风险情景 0 负值 |
| 10 | 批量资源假象 | 每泊位岸桥按一批订货、产线上限 6 → 4 台/泊位时只能一泊位一批，6 泊位一次建成 87 个月 | 核对“批量 ≤ 上限”；全参数扫描能把这种假象翻出来 |
| 11 | getter 被拍平 | `Object.assign(S, { get Tmax(){} })` 存的是当时的值，审计拿到旧 Tmax | 用 `Object.defineProperty` |
| 12 | 旋转元素包围盒变大 | 45° 水滴图钉包围盒 ×1.41，摆放判圆距、审计判方框，永远“重叠” | 摆放和审计用同一判据（方框）；图钉改圆形 |
| 13 | 网格索引尺度不对 | 公里级场景用 2 m 网格做净空检查要 1.7 s | `SEQ.clearance(plan, cell)` 按场景尺度给格子（码头 25 m → 20 ms） |
| 14 | 场景小面片太多 | 9 个海床 / 水面面片 → 每帧 26 次绘制 | 同材质合并成一个网格 → 16 次（两个半区） |
| 15 | 卡片背景盖住画布 | 3D 区一片空白：画布在 z-index 0，卡片有底色 | 3D 容器背景透明 |
| 16 | 交互测试依赖前一步状态 | “甘特切到 B”无变化：上一步“只看 B”已把焦点设成 B | 每个交互测试前先把相关状态复位 |
| 17 | 共享 Mac 端口 / 路径 | 8818 被别的项目的静态服务占着，返回 404；本地 shell 把 `$HOME` 展开成沙盒路径 | 每个项目自己的端口，`--directory ~/…` 由远端展开；先 curl 自检 |
| 18 | 远程命令输出丢失 | 下载失败时异常吞掉了整个输出 | 下载失败只记一行，输出照常返回（`work/port/rx2.py`） |
| 19 | 长任务超过单条命令时限 | 9 视口审计 150 s，命令 120 s 超时 | 远端后台跑 + 轮询日志（`mbg.sh` / `mpoll.sh`） |
| 20 | **投资人 A/B 仪表盘分散注意力** | 码头小样被否：两套方案并排 + 卡片 + 甘特 + S 曲线，形状几乎没变，眼睛不知道看哪儿 | **一个英雄视图优先**：3D 占满屏、形状变化本身就是信息；数字 ≤ 3 个、字幕 1 行；A/B、假设、明细一律收进二层 |
| 21 | 动的构件（整体提升 / 旋转）用不了“生长”着色器 | 屋盖分区要转 4°、再整体升 D 米 | 每顶点带分组号 `aG`，着色器取 `uG[aG]` 矩阵；同一个姿态函数 `HZ.pose(t)` 同时喂渲染、钢绞线端点、净空审计 → 画面和审计不会对不上 |
| 22 | 包围盒审计误报 | 斜杆 / 跨格弦杆的 AABB 把整格框住，柱孔、胎架“撞了” 494 次 | 杆件按“线段 + 半径”对盒子做 slab 裁剪（`HZ.segBox`）；格子拆成“格内核心 + 每根跨格弦杆”多个盒子 |
| 23 | 规则推依赖时成环 | “与提升扫掠相交 → 排在整体提升之后”把楼面、柱也连上了（它们本身是提升的前提） | 先求“整体提升的前驱闭包”，闭包里的构件若相交 = 几何冲突（审计报出、修几何），不加依赖 |
| 24 | 物理量太小、看不出“提升” | 规则算出整体提升只有 ~6 m，千米外几乎不动 | 不夸大物理量；改用 **节奏 + 机位**：时间轴给提升段 14× 权重（慢放带标在轨道上），相机在提升段自动切到侧面低机位，杆件放粗到千米外可读、新装构件短暂发光 |
| 25 | 南向英雄机位被前景楼挡住 | 42 个机位变体里，南侧全被 80 m 的云门挡住 | 先做机位 × 时段变体扫描（VM 上 SwiftShader 只看构图，Mac GPU 再定调色），再定默认机位；结论记在 COMPUTE_NOTE |
| 26 | 同一页面只改 hash 不会重新加载 | 变体扫描 42 张图其实只渲染了 5 个状态 | 每个变体用不同的查询串（`?k=<id>#...`）强制重载 |
| 27 | 远端 `bash -c '<cmd>'` 里再套单引号 | Mac 后台任务静默没跑（日志空） | 远端命令里只用双引号；跑前先 `tail` 日志确认在跑 |

## 7. 计算资源：什么时候值得用 Mac / VM（实测，见 `work/port/COMPUTE_EVAL.md`）

| 任务 | 只用沙盒 | + Mac | + Mac + 5 VM | 沙盒 + 5 VM（不用 Mac） |
|---|---|---|---|---|
| 全参数扫描 360 配置 × 500 次蒙特卡洛 + 审计 | 124.9 s | 39.1 s | 22.0–23.0 s | **11.2 s** |
| 9 视口界面审计 + 37 项交互 | 不能（沙盒无浏览器） | 176–181 s | 81–101 s（VM 跑 7 个视口，SwiftShader） | — |
| GPU 帧率 / 截图 | 不能 | 只能在 Mac（同页面无争用 190–206 fps，Mac 上同时跑 Blender 时 105 fps） | — | — |

结论（详见 COMPUTE_EVAL）：
- **值得分出去**：可分片、确定性、输入小的 CPU 任务（参数扫描、蒙特卡洛、全空间审计）。VM 同步 < 1 s，几乎线性加速；结果逐位一致，可以直接合并。
- **Mac 的价值是 GPU，不是 CPU**：Mac 算得最快（296 个配置 14.8 s），但经 tailscale 的 SSH 同步 + 回收每次 15–25 s，短任务里反而成了瓶颈。CPU 任务优先给 VM。
- **界面审计**：DOM / 数字检查可以在 VM 的 SwiftShader 上分视口并行（结果与 Mac 一致，用来加速迭代）；验收（0 问题、帧率、截图）必须在 Mac 真 GPU 上跑。
- **不值得分出去**：单个配置的排程（几十毫秒）、改代码后的冒烟测试（同步开销 > 计算）、需要人看的截图。
